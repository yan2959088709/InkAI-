# InkAI 1.0 质量基准报告

> 这是 InkAI 系统从"生成混乱小说"演进到"出厂干净小说"后，
> 用工程化指标完成的**修复前后量化对照**。
>
> 对比对象：
> - **《暗夜追凶》（50 章 / 125,814 字）** —— 旧管道遗留，包含 character/storyline 数据契约断裂、跨章场景突跳等已知问题
> - **《青冥录》（30 章 / 60,729 字）** —— 全部由新管道一次出厂，零人工介入，零重写
>
> 所有指标由 `run_full_novel_audit.py` 计算，纯本地零 LLM 成本，可重复运行。
>
> 最后更新：2026-04-27

## 关键洞察

### 1. M6 风格连续性 +48 —— 本轮修复的最大价值

`run_chapter_demo.py` 的 F1-F4 改造（recent_chapters 30K 字预算 / 末位 400 字 prev_anchor / ending_hook 强承接）
**真实地把跨章场景跳跃从结构性问题压成了 0**：

| | 4-gram 实体延续断点（首段无任何 4 字连续片段在末段出现）|
|---|---:|
| 《青冥录》30 章 | **0 处** |
| 《暗夜追凶》50 章 | **6 处**：→ch3、ch4、ch9、ch19、ch21、ch22 |

抽样验证：

> 《暗夜追凶》ch2 末段：「季沉将侧写报告推过桌面，沈夜的目光越过纸张，**落在窗外被雨水模糊的旧港区轮廓上**。」
>
> 《暗夜追凶》ch3 首段：「**春江市公安局技术科实验室的恒温系统**开到了最低档，冷风贴着防静电地板游走……」

→ 完全切换场景，钩子词没有任何重现。

> 《青冥录》ch12 末段：「……**渊顶传来执法堂破开禁制的沉闷轰鸣**。」
>
> 《青冥录》ch13 首段：「**渊顶的沉闷轰鸣尚未彻底消散**，顾长歌已如一道灰影掠过坠星渊边缘的断崖……」

→ 钩子句直接化用为下章首句，实体（"渊顶"、"沉闷轰鸣"）100% 承接。

### 2. M4 跨章档案 +4 —— canon 校验 + 硬约束注入的胜利

| | 跨章扫到的"未注册具名角色" |
|---|---|
| 《青冥录》30 章 | 0 个真问题（仅"安分守己"成语被 1 章误识别）|
| 《暗夜追凶》50 章 | 1 处：「李曼」@ch3 |

注：《暗夜追凶》storyline.json 中还藏着林振国、苏瑾、陈默 3 个未注册具名角色（由 `run_validate_canon.py` R005 暴露）—— 这部分由档案校验器把守，audit 工具与 canon checker 各司其职。

### 3. M5 伏笔账本均 100 —— OutlinePlanner ledger 的结构正确性

两本都通过：
- 没有 plant_volume > payoff_volume 的时序矛盾
- 所有伏笔关键词都能在某章正文中找到 3 字粗匹配

更深层的"伏笔是否真被回收"由卷级 `VolumeValidator.cross_volume_consistency` 检测，
属于另一条质量保障路径。

### 4. M2 / M3 都 100 —— 主角连续 / 钩子互异

新流程的两个隐性贡献：
- 主角必现校验（ChapterCardWriter 内置）确保了主角戏份不脱轨
- ending_hook 卷内不重复约束（OutlinePlanner 内置）确保了 30/50 章每个钩子都不雷同

## 工具链全景

本次修复后，整套质量保障已经形成三层防线：

```
Init 阶段（出厂前防御）
  ├─ canon_checker.py：6 条规则的档案一致性硬校验（R001-R006）
  └─ run_init_novel.py --strict-canon：发现 ERROR 直接拒绝出厂

Generation 阶段（生成时硬约束）
  ├─ characters.json + storyline.json → OutlinePlanner prompt 注入
  ├─ chapter_card.must_appear → ChapterCardWriter 角色档案精挑
  └─ recent_chapters + prev_anchor → 末段实体强承接

Audit 阶段（出厂后体检）
  ├─ run_validate_canon.py：单 novel 一致性快检
  ├─ run_validate_volume.py：卷级综合得分（VolumeValidator）
  └─ run_full_novel_audit.py：全本六维纵览（M1-M6）
```
